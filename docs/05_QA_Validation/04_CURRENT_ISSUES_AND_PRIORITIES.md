## 1. 목적

이 문서는 현재 프로젝트의 로드맵, README, QA 문서, 주요 구현 파일을 기준으로 확인된 제품 리스크를 정리한다. Colosseum 해커톤 제출용 데모 완성도와 실제 서비스 운영 준비도를 분리하여, 해커톤 이후 안정화 작업의 우선순위를 명확히 하는 것이 목적이다.

현재 진단은 다음과 같다.

> MVP는 데모 제출용으로는 잘 포장되어 있으나, 실제 서비스로 전환하기 전에는 제품 범위, 결제 신뢰성, AI 도구 호출 구조, 로그인 이후 사용자 여정 검증이 가장 큰 리스크다.

확인한 검증 결과:
- `npm run typecheck` 통과.
- `npm test` 통과. 다만 현재 테스트 명령은 실질적으로 프로덕션 빌드 성공 확인에 가깝고, 지갑·결제·채팅·로그인 후 E2E QA를 대체하지는 않는다.

## 2. 주요 문제점

### 2-1. 제품 범위가 너무 넓다

README는 AI 컴패니언 채팅, Solana Actions, Blinks, cNFT 기억 각인, Token-2022, ZK Compression, Privy 임베디드 지갑, SIWS, 다중 결제 수단을 모두 동시에 “Live” 기능처럼 제시한다.

리스크:
- 신규 사용자가 춘심이와 대화해야 하는 감정적 이유를 이해하기 전에 블록체인 기능 목록을 먼저 보게 될 수 있다.
- 핵심 사용자 루프가 흐려질 수 있다. 즉, 대화하기, 감정적 순간 만들기, 기억 저장하기, 선물하기, 결제하기 중 무엇이 첫 행동인지 불명확해진다.
- 제품 포지셔닝이 AI 컴패니언, 크립토 결제 앱, 팬덤 플랫폼, 해커톤 인프라 데모 사이에서 분산될 수 있다.

권장 방향:
- 첫 제품 루프를 “첫 비밀 대화 -> 감정적 순간 -> CHOCO 액션 -> 기억 저장 또는 선물”로 좁힌다.
- 나머지 Solana 기능은 첫 화면의 주인공이 아니라 핵심 루프를 받치는 인프라로 배치한다.

### 2-2. 문서상 데모 성공과 실제 제품 리스크가 섞여 있다

마스터 로드맵에는 Colosseum E2E 시나리오가 대부분 완료로 표시되어 있으나, 동시에 발견 버그 우선순위화, 402 이후 충전 복귀, 모달 닫기 후 대화 재개, 배포 체크리스트 정리 등이 미완료로 남아 있다.

리스크:
- 데모 성공과 서비스 신뢰성이 같은 완료 상태처럼 보일 수 있다.
- 체크리스트가 완료되어 보여도 운영 리스크가 숨어 있을 수 있다.
- 한 번 성공한 데모 경로를 기준으로 전체 서비스 준비도를 과대평가할 수 있다.

권장 방향:
- 상태 라벨을 `Demo Verified`, `Service Verified`, `Needs Regression`으로 분리한다.
- 로그인된 테스트 유저로 다시 검증하기 전까지 UX 및 결제 복구 항목을 열린 이슈로 유지한다.

### 2-3. AI 도구 호출이 임시 패턴 매칭에 의존한다

현재 자연어 기반 Solana 도구 실행은 LangGraph ToolNode를 통한 정식 LLM Tool Calling이 아니라, `executeNaturalLanguageCommand()`의 키워드 및 정규식 매칭에 의존한다.

리스크:
- 사용자가 조금만 다르게 말하면 잔액 확인, 구매, 체크인, cNFT 각인 흐름이 실행되지 않을 수 있다.
- 반대로 사용자가 명확히 거래성 액션을 의도하지 않았는데도 도구가 실행될 수 있다.
- 다국어 사용자와 다양한 캐릭터 페르소나로 확장하기 어렵다.

권장 방향:
- 정제된 도구 스키마를 기반으로 정식 LLM Tool Calling을 복구한다.
- LangGraph에 ToolNode와 조건부 엣지를 추가한다.
- 슬래시 커맨드는 결정론적 fallback 또는 디버그 인터페이스로만 유지한다.

### 2-4. 결제 검증은 실서비스 수준으로 더 강화해야 한다

현재 Solana 서명 검증 흐름은 트랜잭션 존재 여부와 수신 지갑의 잔액 증가분을 확인하지만, 생성된 결제 레코드와 온체인 트랜잭션의 연결을 더 강하게 검증해야 한다.

리스크:
- 결제 생성 시 발급한 reference public key가 실제 트랜잭션에 포함됐는지 명시적으로 검증해야 한다.
- 결제 상태, 트랜잭션 해시 중복, payer identity, 결제 생성 시각 이후의 트랜잭션인지 여부를 일관되게 확인해야 한다.
- DB에는 CHOCO가 지급됐지만 이후 SPL CHOCO 전송이 실패하면 앱 내부 잔액과 온체인 잔액이 어긋날 수 있다.

권장 방향:
- reference public key, 수신 지갑, 기대 lamports, payer, 결제 생성 시각, 중복 signature를 모두 검증한다.
- DB 지급과 SPL 전송의 reconciliation 상태를 관리자 화면 또는 로그에서 확인 가능하게 만든다.
- DB CHOCO가 source of truth인지, SPL CHOCO가 source of truth인지, 또는 둘 모두를 정합성 있게 맞출 것인지 정책을 확정한다.

### 2-5. 지갑 및 환경 설정이 데모 지향적이다

Privy App ID와 devnet RPC URL이 provider 코드에 하드코딩되어 있다. 로드맵에도 `VITE_PRIVY_APP_ID`가 하드코딩되어 있어 환경변수가 불필요하다고 기록되어 있다.

리스크:
- 데모에서 운영, 또는 devnet에서 mainnet으로 전환할 때 환경 분리가 취약하다.
- Privy 프로젝트, RPC provider, 네트워크를 바꾸려면 설정 변경이 아니라 코드 변경이 필요하다.
- 배포 리뷰 시 어떤 값이 환경별 설정인지 파악하기 어렵다.

권장 방향:
- 공개 클라이언트 설정은 명시적인 `VITE_*` 환경변수로 이동한다.
- devnet/mainnet 선택을 하나의 설정 레이어에서 확인할 수 있게 만든다.
- 서버 측 secret과 클라이언트 공개 설정 모두에 대해 시작 시점 검증을 추가한다.

### 2-6. 서버 지갑 의존도가 높다

신규 지갑 온보딩 시 서버 지갑에서 0.5 devnet SOL을 전송한다. 이 흐름은 서버 지갑 잔액에 의존하며, 실패해도 사용자 가입 흐름은 막지 않고 로그만 남긴다.

리스크:
- 서버 지갑에 SOL이 부족하면 데모 온보딩은 조용히 결제 불가능 상태가 될 수 있다.
- 사용자는 로그인은 되었지만 Solana 액션을 완료하지 못할 수 있다.
- 제품 경험이 중앙화된 운영 지갑의 잔액 상태에 묶인다.

권장 방향:
- 사용자가 결제 또는 Solana 액션을 수행해야 하는 시점에는 온보딩 funding 상태를 명확히 보여준다.
- 관리자용 서버 SOL 및 CHOCO 잔액 모니터링을 추가한다.
- 자동 devnet funding은 데모 전용 동작으로 제한하고, mainnet 전환 전에는 제거하거나 명확한 플래그로 격리한다.

### 2-7. 로그인 이후 UX가 충분히 깊게 검증되지 않았다

기존 UX 검증 문서는 초기 렌더링, 로그인·온보딩 표면, 인증 가드 중심으로 확인되었다. 문서 자체도 실제 내부 화면에 대한 깊은 검증을 후속 과제로 남겨두고 있다.

리스크:
- 가장 중요한 흐름인 채팅 스크롤, 말풍선 가독성, 지갑 서명 체감 속도, 결제 복구, 기억 앨범 확인이 충분히 검증되지 않았다.
- 사용자는 왜 CHOCO가 필요한지, 충전 후 어떻게 원래 대화로 돌아가는지 이해하지 못할 수 있다.
- 모바일 사용자는 지갑, 모달, 채팅 전환 과정에서 마찰을 느낄 수 있다.

권장 방향:
- 테스트 계정을 사용하는 로그인 후 E2E QA 스크립트를 만든다.
- 모바일 viewport를 우선 기준으로 검증한다.
- “채팅 -> 402 잔액 부족 -> CHOCO 구매 -> 원래 대화 복귀 -> 메시지 전송 -> 기억 각인” 순서를 최우선 검증 경로로 삼는다.

## 4. 관점별 정리

### 4-1. 기획 관점

핵심 문제:
- 프로젝트의 내러티브는 강하지만, 동시에 증명하려는 포인트가 너무 많다.

결정해야 할 질문:
- 첫 제품은 비밀스러운 AI 컴패니언인가, 팬덤 경제인가, Solana 관계 레지스트리인가?
- 사용자는 첫 3분 안에 어떤 행동을 해야 하는가?
- 심사위원에게 보여줄 기능과 실제 결제 사용자에게 필수인 기능은 무엇인가?

즉시 필요한 기획 작업:
- 전체 Solana 기능 목록이 아니라, 하나의 수익화 가능한 사용자 루프를 중심으로 서비스 준비 로드맵을 다시 정리한다.

### 4-2. 코드 및 아키텍처 관점

핵심 문제:
- 코드는 컴파일되고 빌드되지만, 핵심 경로에는 아직 데모 시기의 shortcut이 남아 있다.

가장 위험한 영역:
- Solana 결제 검증.
- DB 잔액과 SPL 전송의 정합성.
- 정규식 기반 자연어 도구 실행.
- 환경 설정과 네트워크 전환 구조.

즉시 필요한 엔지니어링 작업:
- 기능 확장보다 결제 검증 강화를 먼저 처리한다.

### 4-3. 사용자 편의 관점

핵심 문제:
- 앱은 시각적으로는 완성도가 있지만, 로그인 이후 사용자 여정은 아직 직접적인 검증 근거가 부족하다.

가장 위험한 순간:
- 첫 채팅에서 CHOCO가 필요하거나 402를 만나는 순간.
- Phantom과 임베디드 지갑 중 무엇을 선택해야 하는지 판단해야 하는 순간.
- CHOCO를 충전한 뒤 원래 대화로 돌아가야 하는 순간.
- 기억을 저장한 뒤 앨범에서 실제로 확인해야 하는 순간.

즉시 필요한 UX 작업:
- 감정적 순간에서 거래로 이어지는 전체 흐름을 모바일 우선 수동 QA 시나리오로 만든다.

## 5. Global Rubric Scorecard

| Rubric | 현재 평가 | 리스크 | 다음 개선 |
| :--- | :--- | :--- | :--- |
| Functionality | 빌드와 타입체크는 통과하며 데모 경로가 존재한다. | 로그인 후 E2E와 결제 edge case가 자동화되어 있지 않다. | 채팅, 결제, 지갑, 기억 앨범에 대한 서비스 수준 E2E를 추가한다. |
| Potential Impact | 실존 팬덤 IP와 글로벌 크립토 레일은 잠재력이 크다. | 범위가 넓어 첫 사용자 가치가 흐려질 수 있다. | 사용자에게 보이는 핵심 루프를 집중시킨다. |
| Novelty | AI 관계 기억을 Solana에 연결하는 접근은 차별적이다. | 감정에 고정되지 않으면 기능 나열처럼 보일 수 있다. | 관계와 기억을 먼저 보여주고, 이후 체인의 필연성을 설명한다. |
| UX | 시각적 완성도와 온보딩 표면은 강하다. | 로그인 이후 내부 흐름 검증이 부족하다. | 모바일에서 402 -> 충전 -> 대화 복귀 경로를 검증한다. |
| Open-source | 스택은 현대적이고 조합 가능성이 높다. | 하드코딩 설정과 데모 전용 흐름은 이식성을 낮춘다. | 설정을 env로 이동하고 로컬/운영 설정 문서를 정리한다. |
| Business Plan | CHOCO, 선물, 구독, 기억 각인이 수익화 경로를 제공한다. | 실제 가치가 걸리기 전 결제 신뢰성과 reconciliation이 강화되어야 한다. | DB/온체인 source of truth와 정합성 정책을 확정한다. |

Coverage:
- 6개 루브릭 중 최소 4개 이상은 적극적으로 다뤄지고 있다. 다만 서비스 출시 전에는 Functionality, UX, Business Plan 영역의 안정화가 필요하다.

## 6. Originality and Ethics Check

Originality:
- 이 프로젝트는 실존 팬덤 IP, AI 컴패니언 채팅, Solana 기반 관계·기억 메커닉을 결합한 독자적 제품 컨셉을 가진다.
- 가장 강한 독창성은 일반 AI 채팅이 아니라, 감정적 연속성과 검증 가능한 기억 소유권의 결합에 있다.

Ethics and user trust:
- 이 제품은 친밀한 대화, 결제, 지갑 identity, 기억 기록을 다룬다. 따라서 명확한 사용자 동의와 신중한 프라이버시 문구가 필요하다.
- cNFT 기억 각인은 mint 전에 영구성을 명확히 알려야 한다.
- 결제 및 지갑 흐름은 devnet 데모 자산이 실제 가치가 있는 것처럼 오해하게 만들면 안 된다.

필수 가드레일:
- 기억 각인 전 명확한 확인 절차.
- devnet 데모 토큰 동작과 향후 mainnet 가치의 명확한 분리.
- 채팅 기억, export, reset, deletion에 대한 투명한 프라이버시 설명.
